Delivery OS — implementation plan

Ten sprints to the seventeen-step process

This delivers the delivery process on the infrastructure THCO already runs, checked against the full 34-page master specification as well as the three diagrams. The enterprise platform and intelligence layer the specification describes are a separate track with their own budget, deferred here with reasons rather than dropped. Bundling the two is how this stalls.

10 sprints · 20 weeks · one engineer No parallel feature work assumed Reference: docs/DELIVERY_OS_SPRINT_PLAN.md
Sprint 0

Three questions block starting

None of these are engineering questions, and each one changes the shape of the work. Sprint 1 should not open until they are answered. A fourth question stood here — whether "Crowther Delivery OS" was THCO's own system or a different organisation's. It is resolved: Crowther is THCO. Confirmed directly (20 August 2026) — this is THCO updating and bringing the new changes to itself.

QuestionWhy it blocks
Does the talent database stay inside this system? The diagrams show "HR / Talent Systems" as an external integration, and the specification's own 31-entity data model has no candidate, resume or sourcing entity anywhere in it. Today it is 33,547 candidates and ~21 GB living inside this application. Moving it out is a project that dwarfs this one.
Which of the twelve roles are actually staffed? The current seven-flag role model already failed for this exact reason — the stage-2 and stage-5 gates were removed from the code because nobody held the flags. Building gates for unstaffed roles repeats that mistake.
Does step 11 carry a contract, or is commercial work outside this flow entirely? The three diagrams label step 11 "Validation & Commercial Readiness," owned by TSD + Legal + Finance. The specification's own text states the opposite as a deliberate change — "commercial/finance administration is outside the core technical Delivery OS flow" — and gives step 11's owner as TSD + Client only. Sprint 9 cannot be scoped correctly until this is settled.

The rule that follows from question 2: a role that is not staffed gets modelled but not gated. Record who did the work; do not block the step on a flag nobody carries.

Sequence

Twenty weeks, and where the risk sits

Sprint 2 is the one you can move. Nothing else depends on it. It sits second because the reliability debt is live — storing 21 GB of files in the operational database is what took the cluster down on 19 August. If leadership wants visible process progress first, swap it with Sprint 3 and run it later.

The work

Sprint by sprint

01WEEKS 1–2

Safety net

Low risk

Goal: be able to change flow.py without guessing what broke.

  • backend/tests/ already holds 17 test files. Nothing runs them — .github/workflows/ has only deploy and scheduled jobs. Add a CI workflow running pytest on every push and PR
  • Fix or quarantine what currently fails, with a note per quarantine
  • Move the by-hand verification scripts into the repo — they already cover 144 rules across permissions, attachments, stage transitions and unit heads
  • Pin current stage behaviour, including the stage-5 split, so Sprint 3 has a baseline to diff against
Done whenCI is green on main, and a deliberate break in STAGES turns it red.
ReviewThe Actions tab, not the browser.
02WEEKS 3–4

Files out of the database

Medium risk

Goal: stop storing binaries in the operational database.

  • task_attachments writes raw bytes straight into the Mongo document. resume_files does the same at scale — 65,278 files, ~21 GB
  • Add a blob-storage service (Azure Blob, same subscription) behind one interface
  • Write new files to blob; read from either during migration
  • Backfill in throttled, checkpointed chunks, overnight — the discipline the CV migration learned the hard way
  • Leave profile photos as data URLs. They are small, and the authenticated-<img src> constraint is real
Done whenNew uploads land in blob, old ones still open, collection size drops as the backfill runs.
ReviewUpload an attachment to a task card, open it, delete it. Then open an old CV.
03WEEKS 5–6

The seventeen-step model

High risk

Goal: the pipeline is seventeen steps, and the fifteen live projects survive it.

  • Rewrite STAGES in backend/routers/flow.py and frontend/src/pages/flow/stages.js — these two must stay in sync
  • Extend LEGACY_STAGE_MAP so every current stage lands somewhere sensible
  • Retire the stage-5 split. Today a project forks into two sibling records; the new flow is one. Write the merge, rehearse it against a copy of production, keep the sibling ids for traceability
  • Rework the transition validators and the payload whitelist for the new gates
  • Update _send_stage_email for seventeen steps and their new owners
Done whenAll 15 live projects render with no orphans, and Sprint 1's baseline passes in rewritten form.
Review/flow — the board and each project detail page. Move one forward and back.
RiskA data migration against live work. Snapshot the database first and rehearse the merge.
04WEEKS 7–8

The board, and seventeen columns

Low risk

Goal: seventeen steps a human can actually read.

  • Ten columns already fill a screen. Seventeen equal columns behind a horizontal scroll is a spreadsheet, not a pipeline
  • Group the board by the five phases; collapse completed ones, keep the active one open
  • Show the validation gate on the board. Pre-validation and post-validation work should not look identical
  • Update FlowProjectDetail.jsx and StructuredStageModal.jsx for the new gates
  • Honour the house rules: pale-wash icon badges, dialogs naming their own bg-white, inputs carrying bg-white text-gray-900
Done whenA manager sees where every project is without scrolling sideways.
Review/flow on a narrow window as well as a wide one.
RiskLow technically, high on opinion. Show a mockup before building it.
05WEEKS 9–10

Roles and ownership

Medium risk

Goal: the TSD owns the project from step 03 to step 17, and the system knows it.

  • Introduce the TSD as the owning role, absorbing today's delivery_owner_id
  • Add Solution Architect, Product Designer and QA Lead — modelled, not gated
  • Retire the dead flags. is_delivery_coordinator is held by nobody, is_engineer by one person; both gates are already gone from the code and the flags now only mislead
  • Build the step-06 architect request: the ask, optional Senior Partner approval, assignment, brief delivered
  • Manager grants come from two places — collapsing them once stripped every manager in the firm. Call clear_user_cache() on anything that moves ownership
Done whenA project shows one accountable name at every step, and an architect request goes out and comes back.
Review/flow/roles-admin, then run a project from 01 to 06.
RiskPermissions is where this codebase has been wrong most often.
06WEEKS 11–12

Definition artefacts

Low risk

Goal: capture the brief properly, and turn it into a defined outcome.

  • Step 01 — intake form. Project template, desired outcome, call transcripts, supporting documents, client context. Reuses the attachment infrastructure, now on blob storage
  • Step 05 — outcome brief. Problem statement, defined outcomes, success metrics, scope boundaries, assumptions, risks, constraints
  • Both are forms plus documents on a project. No new storage, no new services
Done whenA project created from the new form carries everything a TSD needs without a single email.
ReviewCreate a project at /flow/new-project, then write its outcome brief.
07WEEKS 13–14

Design artefacts

Low risk

Goal: build the phase that does not exist today.

  • Step 07 — scoping document. User needs, process flows, feature list, effort estimate, roadmap
  • Step 08 — architecture record. Tech stack, integrations, data architecture, security and compliance review, high-level estimate
  • Both attach to the project, both owned by the Solution Architect
Done whenA project carries a real scope and a real architecture, and the estimate is a number the system holds.
ReviewRun a project through 06 → 07 → 08 with an architect account.
RiskThe highest-value sprint here and the least technically difficult. That is a good sign, not a suspicious one.
08WEEKS 15–16

Demo, the loop, and the exit

Medium risk

Goal: iterate with the client, and be able to stop.

  • Step 09 — demo artefact. Wireframes, prototype link, walkthrough notes, and which version the client saw
  • Step 10 — feedback and change log. Each round numbered; the 10 → 09 loop is a real transition, not a stage revert
  • The pre-validation kill switch. The flow as drawn has no exit before step 11's CLIENT VALIDATED gate. Extend today's mark_lost into a proper stop at any pre-validation step, with a reason
  • Start recording pre-validation effort. Steps 01–10 are spent before the client has validated anything, and someone will eventually ask what that costs — whether or not a contract also sits at step 11
Done whenA project can go round the demo loop three times with a legible history, or be stopped at step 07 with a reason.
Review/flow/projects/{id} — the history should read as a story.
RiskThe loop is the one place the state machine stops being linear.
09WEEKS 17–18

Client validation and the POD

Medium risk

Goal: the client formally validates, scope freezes, and a named team forms.

  • Step 11, core version. The client confirms final direction, scope and acceptance criteria; the project is marked CLIENT VALIDATED. Scope freezes here regardless of how blocker 3 resolves
  • Step 11, commercial extension — only if blocker 3 resolves that way. Commercial proposal, legal review, contract preparation. Today's stages 6, 7 and 8 already cover most of this, so it would be a consolidation, not a build. If the specification's reading wins instead, this half does not happen here and Legal/Finance stay outside the flow
  • Step 12 — POD. The delivery team as an object: members, roles, resourcing, kickoff date, delivery plan. Not just a list of collaborators
Done whenA validated project refuses a scope edit and offers a change request instead, and a POD is a thing you can open.
ReviewTake a project through 11 into 12, then try to edit its scope.
RiskScope freeze is a new rule for this codebase, and this sprint cannot be scoped precisely until blocker 3 is answered.
10WEEKS 19–20

QA, acceptance, handover, closure

Low risk

Goal: the project ends properly, and the ending feeds the next one.

  • Step 14 — QA. Test plan, execution results, defect tracking. Today this is a build_status reading ready_for_qa; it becomes an owned step
  • Step 15 — acceptance. Criteria agreed back at step 11, who signed, when, against which build
  • Step 16 — handover. Knowledge transfer, documentation, training, operational readiness
  • Step 17 — closure. Closure report, lessons learned, archive, repository cleanup. projects_archived already exists and is reusable
Done whenA project can be closed, and the closure report answers "did we do what we said we would."
ReviewRun one project end to end, 01 to 17.

Step 13 has no sprint. Engineering / Build is already covered by the task board — cards with labels, assignees, priorities, due dates, attachments and covers. It is the one part of the delivery flow THCO already does well, and the plan leaves it alone.

Checked against the specification

Where these ten sprints sit in the spec's own five-tier plan

A 34-page master specification was supplied after the first draft of this plan. It lays out its own five-tier MVP sequence and states the build rule behind it directly: "Do not attempt to build every feature simultaneously. Establish the operating architecture, build the control system, test it, then expand." These ten sprints are an execution of that rule against THCO's actual codebase — not a competing plan.

Specification tierWhat it coversWhere it sits here
MVP 1 — Project Control System Auth, roles, clients, projects, TSD assignment, stages, gates, dashboard, tasks, milestones, documents, activity log, What Next? Sprints 1–5. "What Next?" as a real recommendation engine is not built here.
MVP 2 — Product + Architecture Discovery, Product Brief, requirements, journeys, Architect request/selection, architecture, diagrams, versions, decisions Sprints 6–7 cover the artefacts. Versioned diagrams and a structured decision log are not.
MVP 3 — Demo Loop Model tracking, design review, demo workspace, feedback, AI change analysis, validation gate Sprint 8 covers the artefact, feedback log and loop mechanics. AI change analysis — automatically classifying feedback and running impact analysis — is not built and has no obvious owner yet.
MVP 4 — Delivery Orchestration TalentSD, People & Operations, Legal, pod formation, engineering, QA, scope changes Sprint 9 covers POD formation and scope freeze. TalentSD and People & Operations as active participants, not just named roles, are not built.
MVP 5 — Intelligence Recommendations, risk, scope, dependency, resource intelligence, portfolio control tower, learning loop Entirely out of scope. The ten-agent AI layer, the Knowledge Graph, the Risk/Dependency engine and the Control Tower — see delivery-os-flow.html §07.

The honest summary: these ten sprints deliver MVP 1 and MVP 2, most of MVP 3, and the structural half of MVP 4. They do not touch MVP 5 — which is roughly half of what the full specification describes by page count. Anyone asked "how far along is the Delivery OS after these ten sprints" should hear that number, not "the process is done." The process is done; the operating system the specification describes is not.

Deferred track

Not "no" — later, and why

ItemReason
Data access layerWorth doing on its own merits, and it turns the eventual Postgres move from a full rewrite into one layer. But it is 3–4 weeks producing nothing a user can see, and it should not sit between the firm and a working process. Slot it after Sprint 10.
PostgreSQL migrationAlready costed at 6–9 weeks for one engineer, doubling if feature work continues. A project, not a sprint.
Client portalThe right next thing after the process lands — it unlocks steps 10 and 15 and it is the first thing clients ever see. It is also the first externally-exposed surface this system has had, which brings authentication, rate limiting and a security review with it.
AI TSD assignment (step 02)Cannot work yet. Ranking on expertise, capacity and delivery history needs data that does not exist — no skill or capacity records on any user, and 15 projects total. The seventeen steps are what generate that data.
What-Next engine, knowledge graph, copilotSame reason. They read structured history the process has not yet produced.
OpenSearch, Redis, data warehouseMongo's $text index and the 45-second in-process identity cache are adequate at this size. Revisit when they demonstrably are not.
Multi-AZ Kubernetes, WAF, IDS, Prometheus/ELKEnterprise infrastructure for 30 users and 15 projects, against a system that currently scales to zero overnight to save money. Destinations, not next steps.
SSO / MFAWorth doing and cheap relative to the rest. Reasonable to pull forward if the security posture is questioned — it is not sequenced here only because nothing else depends on it.
Standing risks

True across the whole plan

  • flow.py is 89 KB and every route in it passes through _get_user. Sprints 3, 5, 8 and 9 all edit it. Sequence them; do not run them as parallel branches.
  • Merge each sprint into main on its own. Do not accumulate ten sprints of change and integrate at the end.
  • Every push to main deploys, and there is no staging environment. Each sprint's merge is a production release and needs the same care.
  • The database is one burstable vCore. Sprint 2's backfill and Sprint 3's migration are both bulk writes. Overnight, throttled, checkpointed.
  • Test scripts that appoint a unit head must restore it however they exit — via atexit, not the end of a function. This has already silently removed a real manager's rights once.
  • Verify against the page, not only the API. A payload correct in isolation once crashed the calendar because its only consumer read different field names, and an API-level check called that verified.
Out of scope

What this plan does not answer

  • Whether the firm has the people to staff the process — the third blocking question, and the one most likely to be answered late.
  • Whether step 11 carries a contract at all — unresolved between the diagrams and the specification; Sprint 9 is written to accommodate either answer.
  • What pre-validation investment THCO is willing to make per deal. That is the commercial question underneath the entire flow, and no amount of software settles it.
  • Whether the ten business units survive a model organised by role and project rather than by unit. The diagrams have no unit concept at all. This plan leaves the units alone and assumes the question comes later.
